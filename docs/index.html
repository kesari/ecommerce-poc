If I change this, what else breaks?

We are testing whether a repository tool helps an agent identify cross-repository changes more completely than the same agent working alone.

Updated 20 October 2026. Twelve cases are runtime-verified. The 144-attempt comparison has not run; paid execution is disabled. Read the full checkpoint.

What we need to learn

A useful answer identifies what breaks after a proposed change, the contracts carrying that change, the production edits needed to repair it, and the repositories that need validation without edits. Finding a few related files is not enough.

The e-commerce estate is the test fixture: ten repositories connected through Java clients, REST, Kafka, a proxy and a React storefront. Expected answers stay outside the searchable source estate.

Establish behavior before scoring an answer

Pinned baseline→Proposed change→Repair or compatibility proof→Reject a wrong variant

The twelve cases cover HTTP bindings, web consumption, Kafka, amount units, delivery policy, private SQL/cache changes and compatible controls. Kafka, PostgreSQL and Valkey cases use real dependencies on the stated test boundaries. Understand what is proved and scored.

What the results say today

Two fresh product reruns on one guided REST case accepted the required bounded repair. They do not establish improvement over agent-only. Historical simulation scores used harness-built indexes and cannot justify adopting a real product.
